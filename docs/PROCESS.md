## 迭代协议

每个迭代开始前，规划者必须制定迭代协议，包含：

- 迭代目标
- 迭代范围
- 实施计划
- 交付物
- 退出标准

开发者按迭代协议开发；评估者按迭代协议和退出标准校验，发现问题反馈给对应开发者修改，通过后进入下一迭代或阶段验收。

迭代协议一律落盘到 `docs/construction/<迭代号>-<主题>.md`（沿用既有约定，G/H 系列同样放此目录，不另建目录）。

## 迭代分类与评估策略

> 本节由 H2 迭代确立，解决此前"哪些迭代需要独立评估报告"没有明文规则、导致 goal 系列 7 轮零评估工件的问题。

### 三类迭代

| 类别 | 前缀 | 定义 | 迭代协议 | 独立评估报告 |
|---|---|---|---|---|
| 构建迭代 | `C` | 新建责任区块、引入新抽象层、或需跨多个角色协作 | **必须** | **必须**（`docs/construction/c*-evaluation.md`，由评估者角色出具） |
| 目标迭代 | `G` | 在已验收架构内做增量功能，单一角色可完成，退出标准能被自动化验证完全覆盖 | **必须** | 不要求，走自验 |
| Harness 迭代 | `H` | 只改过程工件与文档，零生产代码改动 | **必须** | 不要求，但必须刷新 `evaluator-rubric.md` |

**为什么 G 类可以免独立评估报告**：这类迭代的退出标准本身就是可执行的断言——`npm run test:unit` 的通过数、`tsc --noEmit` 的错误数、`npm run build` 的包体积、`npm run eval` 的命中率、端到端 smoke 的实际返回值。这些数字任何一个后续会话都能重跑复现，比一份追述性的评估报告更难造假。独立评估报告的价值在于引入第二双眼睛判断"设计是否合理"，而 G 类迭代不引入新设计决策——它在已验收的架构里填空。

### 自验的最低要求（G / H 类）

走自验不等于免检。以下四项必须同时满足，缺任一项该迭代不得标记 `pass`：

1. `docs/construction/<迭代号>-<主题>.md` 迭代协议**先于开发**落盘，含明确退出标准。
2. `progress.md` 留下可复核的验证数值：测试通过数、类型检查错误数、包体积（含与上一轮的差值）、评测命中率、端到端 smoke 的实际返回值。
3. `feature_list.json` 对应条目的 `evidence` 字段非空且指向具体证据。
4. 下方"通用退出检查"的双层可观测性逐条过。

### 升级为独立评估的触发条件

G 类迭代命中下列任一条，**必须**升级为出具独立评估报告，不得走自验：

- **破坏性接口变更**：已有函数签名、HTTP API 契约、或 IPC 协议的不兼容修改。
- **持久化 schema 迁移**：SQLite schema、ES mapping、或配置文件 schema 的版本变更。
- **新增数据源类型或 embedder 后端**：扩充 `datasources` / `embedding` 的类型枚举。
- **触及安全边界**：凭证存取、进程边界、文件系统访问范围的变更。

理由：这四类改动一旦出错，代价不由当轮承担，而是转嫁给未来的会话或用户数据。自动化断言只能证明"当前测试通过"，证明不了"迁移路径对老数据安全"。

### G1-G7 追认

G1-G7 在本政策确立之前完成，其中 G1-G4 无迭代协议文档、G1-G7 全部无评估报告。**统一追认为自验通过**，本政策自 H2 起对新迭代生效，不回溯补写。

追认依据：G1-G7 的验证数值均已记录在 `progress.md`，且在 H1 轮经实测复核——144 passed、`tsc` 0 errors、Vite 158.61 kB、`eval:mock` 9/10、19 类结构化日志事件逐个 grep 命中，追溯链完整未断。

**留档判例**：G6 若按上述升级条件衡量，同时命中"破坏性接口变更"（`IndexingPipeline.on_progress` 从 `Callable[[float], None]` 改为 `Callable[[ProgressEvent], None]`）与"持久化 schema 迁移"（`TaskStore` v1 + `ALTER TABLE` + `PRAGMA user_version=1`），本应出具独立评估报告。此处不回溯补写，但记录在案，作为政策生效后的判定参照。

## 通用退出检查

任何迭代的退出标准除了完成迭代协议中的交付物外，还必须通过以下通用检查。这些检查与 `evaluator-rubric.md` 的可观测性维度一一对应，缺一不可：

- **运行时可观测性**：系统层的信号（日志 / 追踪 / 进程事件 / 健康检查）覆盖关键路径并能留证，回答"系统做了什么"。
- **过程可观测性**：本轮迭代的计划、评分标准、验收条件齐备且彼此对齐，回答"为什么这个变更应该被接受"。

未通过上述任一检查的迭代，评估者不得放行；交由对应开发者补齐后再次校验。

## 记录口径约定

> 本节由 H2 迭代确立，来自 H1 复核时发现的两处口径漂移。

- **测试数一律以根级 `npm run test:unit` 为准**。该命令带 `KB_MILVUS_URI=./kb_milvus_lite.db`，Milvus 适配器的 8 项会全跑；直接跑 `pytest` 而不带该环境变量时 conftest 会 skip 这 8 项，导致记录偏低。G7 记录的 "136 passed" 与实测 144 的差值正是此因。
- **包体积以 `npm run build` 输出的 Vite JS 行为准**，记录时带上前一轮数值与差值（如 `153.74 → 158.61 kB（+4.87 kB）`），便于看出趋势。
- **`evaluator-rubric.md` 在每轮迭代收尾时同步**。连续两轮未同步，即视为过程可观测性不合格——该表在 T1 到 G7 之间滞后了 6 轮，是 H1 把过程可观测性评为 3/5 的主要依据之一。
- **新增维度不得长期挂"待评分"**。若某维度因条件不具备而暂缓评分，必须在表中写明解除条件与预计轮次；双层可观测性两维度曾以"待下一轮迭代评分"悬空 7 轮。
